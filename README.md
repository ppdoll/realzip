# 아파트 실거래가 · 예상 시세

국토교통부 실거래 신고 데이터로 **최근 3년 아파트 매매가**를 보고, 그 데이터로
**예상 실거래가**를 계산하는 웹앱입니다. Next.js + TypeScript, Vercel 배포용.

- 시군구 → 단지 → 평형을 고르면 3년 거래내역, 지역 시세 흐름, 예상가가 나옵니다
- 예상가는 80% 예측구간과 신뢰도 등급을 함께 보여줍니다 (숫자 하나만 던지지 않습니다)
- 3개월 후 전망까지 지역 가격지수 추세로 연장합니다
- 우측에 이번 세션에 조회한 단지가 최근 10건까지 쌓입니다 (저장 안 함)
- **전월세**도 같이 봅니다 — 전세 추정 보증금과 전세가율, 최근 1년 전월세 신고 내역

## 1. 시작하기 전에 — API 키 하나가 필요합니다

이건 제가 대신 해드릴 수 없는 유일한 단계입니다. 5분이면 됩니다.

1. [공공데이터포털](https://www.data.go.kr) 회원가입 / 로그인
2. 아래 **두 API 모두** 활용신청 (각각 눌러야 합니다. 둘 다 즉시 자동승인)
   - [국토교통부_아파트 매매 실거래가 상세 자료](https://www.data.go.kr/data/15126468/openapi.do)
   - [국토교통부_아파트 전월세 실거래가 자료](https://www.data.go.kr/data/15126474/openapi.do)

   > 인증키는 하나지만 **활용신청은 API 단위**입니다. 전월세를 신청하지 않으면
   > 매매만 동작하고 전월세 카드에 신청 안내가 뜹니다 (`returnReasonCode 30`).
3. 마이페이지 → 개발계정 → 해당 API → **일반 인증키(Decoding)** 복사
   - ⚠️ `Encoding` 이 아니라 **`Decoding`** 값을 쓰세요. (Encoding 값을 넣으면
     이중 인코딩되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 납니다. 다만
     이 앱은 Encoding 키를 넣어도 알아서 한 번 디코드해 처리합니다.)

```bash
cp .env.example .env.local
```

`.env.local` 을 열어 붙여넣습니다.

```
MOLIT_SERVICE_KEY=여기에_Decoding_인증키
```

## 2. 실행

```bash
npm install
npm run dev
```

http://localhost:3000 → 시군구를 고르고 **조회**.

첫 조회는 36개월을 받아오므로 **20~40초** 걸립니다. 한 번 받은 지역은 이후 즉시 나옵니다.

API 키가 잘 붙었는지 먼저 확인하고 싶다면:

```bash
npm run probe -- 강남구
```

전국 시군구 코드가 다 유효한지 한 번에 점검할 수도 있습니다 (호출량을 꽤 씁니다).

```bash
npm run probe
```

**API 키 없이 돌 수 있는 검증**이 두 개 있습니다.

```bash
npm run check
```

- `smoke` — 연 +9% 로 오르는 가상 시군구를 만들어, 가격지수가 그 궤적을 되찾고
  예상가가 진짜 값의 4% 안에 들어오는지 확인합니다. 표본을 2건으로 줄이면 방식이
  강등되고 신뢰도가 떨어지고 구간이 넓어지는지도 봅니다.
- `rent:check` — 전월세 응답 XML 픽스처로 파서를 검증합니다. 전용면적 태그 철자
  (`exclUseAr` vs `excluUseAr`), 콤마 금액, 빈 태그, 월세 0 = 전세, 단지 이름 매칭,
  전세 추정 정확도까지 고정해 둡니다.
- `render:check` — 차트 컴포넌트를 서버 렌더해 SVG 좌표에 `NaN` 이 새지 않는지,
  점·선·범례가 다 나오는지 확인합니다.

응답 태그명이 바뀐 것 같으면 원본을 그대로 찍어볼 수 있습니다.

```bash
npm run probe -- --raw 11680
```

## 3. Supabase 연결

없어도 돌아갑니다 — 서버 메모리에 캐시합니다. 다만 배포 환경에서는 인스턴스마다 캐시가
따로 생기고 재배포하면 날아가서, 같은 지역을 계속 다시 받아옵니다. 개발계정 일일 한도가
10,000회인데 시군구 하나가 36회이므로, 메모리 모드로 오래 쓰면 한도에 부딪힙니다.

### 용량을 먼저 보세요

무료 티어는 500MB입니다. 실측 기준(강남구 3년 10,484행, 마포구 8,638행)으로 추산하면:

| 담을 범위 | 예상 행 수 | 예상 용량 | 무료 티어 |
| --- | --- | --- | --- |
| 서울 25개 구 | 약 20만 | 약 90MB | 여유 |
| 수도권 (서울·경기·인천 77곳) | 약 54만 | 약 240MB | 절반 |
| 전국 250곳 | 약 150만 | 약 675MB | **초과** |

전월세는 신고량이 매매의 5배 가까이 됩니다(강남구: 3년 69,026행 vs 10,488행). 그래서
**전월세만 창을 1년으로 줄였습니다** — 강남구 기준 69,026행 → 20,433행. 3년으로 두면
서울 25개 구만 담아도 무료 티어를 넘습니다.

창이 매달 굴러가므로 크론이 갱신 후 **1년을 벗어난 전월세를 지웁니다**. 정리하지 않으면
1년 제한이 의미가 없어집니다.

데이터는 조회한 지역만 쌓이므로, 실제로 보는 지역이 몇 곳이면 문제되지 않습니다.
전국을 다 훑을 생각이면 Supabase Pro(월 $25, 8GB)나 별도 프로젝트가 필요합니다.

> **다른 앱과 DB 를 공유하지 마세요.** 실거래가는 데이터가 계속 쌓이는 테이블이라,
> 같은 무료 프로젝트에 운영 중인 다른 서비스가 있으면 그 서비스가 먼저 멈춥니다.

### 연결 절차

1. [supabase.com](https://supabase.com) 에서 **새 프로젝트** 생성
2. Project Settings → API Keys 에서 값을 복사해 `.env.local` 에 넣기

```
SUPABASE_URL=https://xxxxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=eyJ...
```

3. 테이블 생성 — 둘 중 하나만 하면 됩니다.

   **(a) 스크립트로** — 대시보드 → Connect → Session pooler 의 연결 문자열을
   `.env.local` 의 `SUPABASE_DB_URL` 에 넣고:

   ```bash
   npm run db:setup
   ```

   **(b) 손으로** — [`src/lib/schema.sql`](src/lib/schema.sql) 을 SQL Editor 에 붙여넣고 실행.
   (전부 `if not exists` 라서 여러 번 실행해도 안전합니다.)

4. 연결 확인 — 앱이 실제로 쓰는 경로(supabase-js + service_role)로 읽기·쓰기를 시험하고
   적재량과 무료 티어 여유를 알려줍니다. 국토부 API 는 호출하지 않습니다.

   ```bash
   npm run db:check
   ```

### 지역 미리 담아두기

첫 조회가 느린 게 싫으면 미리 받아둘 수 있습니다. 이미 받아둔 달은 건너뛰므로
중간에 끊고 다시 돌려도 됩니다.

```bash
npm run ingest -- 서울            # 시/도 이름으로 (매매 3년 + 전월세 1년)
npm run ingest -- 11110 11140     # 시군구 코드로
npm run ingest -- 경기도 --dry    # 무엇을 받을지만 확인
npm run ingest -- 서울 --rent-only
```

시작 전에 호출 수와 예상 용량을, 끝나고 실제 증가량과 무료 티어 사용률을 알려줍니다.
**전국을 한 번에 담으면 무료 티어를 넘깁니다** — 시/도 단위로 나눠 돌리고 `db:check` 로
여유를 보면서 늘리세요. 지역당 약 6MB(매매 3년 4.5MB + 전월세 1년 1.4MB)라
500MB 로 약 80곳까지 들어갑니다.

`service_role` 키는 RLS 를 우회하므로 **서버에서만** 쓰입니다. `NEXT_PUBLIC_` 접두어를
붙이지 마세요 — 붙이면 브라우저로 노출됩니다. 연결되면 화면 안내에서 "메모리 캐시 모드"
문구가 사라집니다.

`publishable` / `anon` 키로는 동작하지 않습니다. `apt_trade` / `ingest_log` 는 RLS 를 켜고
정책을 두지 않았고(서버만 접근하는 테이블이라 그게 맞습니다), 그 키로 쓰기가 되게 열면
공개 키를 아는 누구나 이 테이블에 값을 넣을 수 있게 됩니다. `db:check` 가 키 종류를
판별해 막습니다.

### 적재 방식 — 월 단위 통째 교체

같은 (시군구, 계약년월)을 다시 받으면 그 달을 **삭제한 뒤 다시 넣습니다.** 부분 upsert 가
아닌 이유가 두 가지 있습니다.

1. **해제된 거래가 원본에서 사라지면 DB 에서도 사라져야 합니다.** upsert 만 하면 취소된
   신고가 남습니다.
2. **동일 키 거래가 실제로 존재합니다.** 같은 단지·같은 계약일·같은 층·같은 면적·같은
   금액인 거래가 여러 건 신고됩니다 (같은 평형의 다른 동). 강남구 2026-05 은 462건 중
   14개 키가 중복이었고, 한 건은 3중복이었습니다. 합치면 거래 건수를 3% 가까이 잃고,
   한 배치에서 같은 키를 두 번 upsert 하면 Postgres 가
   `ON CONFLICT DO UPDATE command cannot affect row a second time` 로 거부합니다.
   그래서 동일 키에는 `#2`, `#3` 접미를 붙여 전부 보존합니다.

월별로 커밋하므로 뒤쪽 달이 실패해도 앞쪽 달은 기록된 상태로 남고, 다음 요청에서
못 받은 달만 다시 받습니다.

### 속도 제한

동시 호출을 6으로 두고 36개월을 몰아 받으면 공공데이터포털이 **HTTP 429** 를 줍니다.
실제로 서초구 수집에서 한 달이 429 로 빠졌습니다. 동시 호출을 4로 낮추고, 429/트래픽 초과에는
일반 오류보다 훨씬 긴 백오프(1.5초부터 배증, `Retry-After` 가 오면 그 값을 따름)를
쓰도록 고쳤습니다. 그래도 36개월 수집은 7~10초에 끝납니다.

한 달이 실패해도 나머지는 정상 적재되고, 실패한 달은 `ingest_log` 에 남지 않아 다음
조회에서 **그 달만** 다시 받습니다. `npm run db:check` 가 지역별 월 커버리지를 보여주니
빠진 달이 있는지 눈으로 확인할 수 있습니다.

### Node 20 에서의 함정

`@supabase/supabase-js` 2.109 는 전역 `WebSocket` 이 없으면 **`createClient` 단계에서
예외를 던집니다.** 이 앱은 Realtime 을 전혀 쓰지 않는데도 클라이언트 생성 자체가 막힙니다.
[`src/lib/supabase.ts`](src/lib/supabase.ts) 가 native `WebSocket` 이 없는 런타임에서만
`ws` 를 transport 로 넣어 우회합니다. Node 22+ 와 엣지 런타임은 native 를 그대로 씁니다.
Supabase 클라이언트는 앱·크론·점검 스크립트가 모두 이 파일 하나를 씁니다.

## 4. Vercel 배포

```bash
npm i -g vercel
vercel
```

또는 GitHub 저장소를 Vercel에 연결하면 push 마다 자동 배포됩니다.

**Project Settings → Environment Variables** 에 넣을 값:

| 이름 | 필수 | 비고 |
| --- | --- | --- |
| `MOLIT_SERVICE_KEY` | ✅ | Decoding 인증키 |
| `SUPABASE_URL` | | 있으면 DB 모드 |
| `SUPABASE_SERVICE_ROLE_KEY` | | 있으면 DB 모드 |
| `CRON_SECRET` | | 넣으면 크론 엔드포인트를 토큰으로 보호 |

### 함수 리전은 서울(icn1)로 고정

기본값(`iad1`, 미국 동부)으로 두면 **느립니다.** 함수가 호출하는 국토부 API 는 한국에,
Supabase 도 서울에 있어서 태평양을 두 번 왕복하게 됩니다. 실측으로 신규 지역 36개월
수집이 **49.4초** 걸렸고(로컬 7~9초) Hobby 의 함수 60초 제한에 거의 닿았습니다.
그래서 [`vercel.json`](vercel.json) 에 리전을 박아 둡니다.

```json
{ "regions": ["icn1"], "crons": [{ "path": "/api/cron/refresh", "schedule": "0 20 * * *" }] }
```

엣지는 원래 서울(`icn1`)로 잡히므로 응답 헤더 `X-Vercel-Id` 가 `icn1::iad1::...` 처럼
두 리전이 다르게 보이면 함수가 아직 미국에 있다는 뜻입니다.

### 크론 — 지역을 나눠 돈다

매일 오전 5시(KST)에 이미 조회한 지역의 최근 3개월치를 다시 받아 늦게 들어온 신고를
반영합니다. 지역이 늘어나면 한 번에 다 돌 수 없으므로(Hobby 함수 상한 60초) 이렇게 돕니다.

- **갱신이 가장 오래된 지역부터** 처리합니다 — `ingest_log.fetched_at` 기준
- 시간 예산 45초가 떨어지면 **새 지역을 시작하지 않고** 멈춥니다.
  도중에 잘리는 것보다 다음 실행에 넘기는 편이 낫습니다
- 남은 지역은 다음 실행이 자연히 뒤에서 이어받습니다.
  **커서 테이블이 없어서** 실행이 끊겨도 상태가 어긋나지 않습니다

실측 지역당 0.6초(빠를 때) ~ 2.5초(느릴 때)라, 한 번에 약 18~70곳을 처리합니다.
그보다 지역이 많으면 며칠에 걸쳐 순환하는데, 활발히 보는 지역은 조회 시점의
6시간 TTL 로도 갱신되니 실사용 영향은 작습니다.

응답으로 무엇이 처리되고 무엇이 남았는지 알려줍니다.

```json
{
  "totalRegions": 6, "refreshed": 1, "remaining": 5, "budgetHit": true,
  "elapsedMs": 2606,
  "results": [{ "label": "서울특별시 마포구", "trades": 315, "staleHours": 18.2, "ms": 2522 }],
  "remainingRegions": ["서울특별시 성동구", "..."]
}
```

수동 실행 시 범위를 좁힐 수 있습니다 (둘 다 기본값보다 크게는 못 잡습니다).

```bash
curl "https://<배포주소>/api/cron/refresh?limit=5"
curl "https://<배포주소>/api/cron/refresh?budgetMs=10000"
```

> Hobby 플랜은 크론이 **하루 1회**로 제한되고 실행 시각이 정확하지 않습니다.
> 함수 상한도 60초라 `maxDuration` 을 60 으로 맞춰 두었습니다. Pro 이상으로 올리면
> `maxDuration` 과 `TIME_BUDGET_MS` 를 같이 올려 한 번에 더 많은 지역을 돌 수 있습니다.

## 5. 예상 실거래가는 어떻게 계산하나

실거래 데이터로 시세를 추정할 때의 진짜 어려움은 세 가지입니다.

**① 단지별 거래가 드물다.** 84㎡ 한 타입이 1년에 2~3건인 단지가 흔합니다.
3년치를 다 써야 표본이 모이는데, 3년 전 가격을 그대로 평균 내면 안 됩니다.
→ 지역 가격지수로 **각 거래를 현재 시점 가격으로 환산**한 뒤 씁니다.

**② 시군구 중위가격은 구성 변화에 휘둘린다.** 이번 달에 비싼 동네가 많이 거래되면
중위가격이 튀는데, 그건 시세 상승이 아닙니다.
→ 같은 단지·같은 평형(unit)이 **여러 번 거래된 기록만** 골라 로그 평단가를
`unit 효과 + 월 효과`로 분해합니다 (2원 고정효과). 교대 중위수로 풀어서 이상거래에
강건합니다. 거래가 1건뿐인 unit은 월 효과에 0만 보태 추세를 눌러버리므로 제외합니다.
마무리 평활은 이동평균이 아니라 **국소선형(LOESS)** 입니다 — 이동평균은 계열의 끝을
안쪽으로 끌어당겨 상승장에서 최근 상승률을 과소평가합니다.

**③ 직거래·가족간 거래·증여성 거래가 시세와 크게 어긋난다.**
→ MAD 기준 이상치 제거 + 직거래 가중치 0.35배 + 해제 거래 제외.

그 다음 단지 시세를 이렇게 뽑습니다.

```
1. 대상 단지 거래 3년치 수집 (해제 건 제외)
2. 지수로 현재 시점 환산:  adj = 평단가 ÷ 지수(계약월)
3. 이상치 제거 (로그 평단가 MAD > 2.5)
4. 가중치 = 최근성(반감기 12개월) × 면적 유사도 × 층 유사도 × 직거래 감점
5. 가중최소제곱:  log(adj) ~ 1 + log(면적/목표면적) + (층-목표층)/10
      ↳ 예측점에서 0이 되도록 중심화했으므로 절편이 곧 추정값
      ↳ 계수를 늘릴 만큼 유효표본이 없으면 항을 하나씩 뺀다
      ↳ 그래도 부족하면 가중 중위수로 강등 (method 값에 표시됨)
6. 80% 구간 = exp(±1.28 · σ · √(1 + 1/n_eff) · (1 + 1.5/n_eff))
      ↳ "다음 거래 1건이 이 범위에 들어올 확률 약 80%"
      ↳ 표본이 적으면 자동으로 넓어진다
7. 3개월 전망 = 지역 지수 최근 12개월 로그추세 연장 (월 ±1.5% 로 제한)
```

`npm run smoke` 가 이 과정을 검증합니다 (위 2절 참고).

### 조회 기록 (우측)

로그인이 없으므로 **저장하지 않습니다.** 페이지를 열고 있는 동안만 React state 로 들고
있고, 새로 고치면 사라집니다 (`localStorage` / `sessionStorage` 도 쓰지 않습니다).

- 단지 조회가 끝날 때마다 단지명·지역·평형·예상가·시각을 최근 **10건**까지 쌓습니다
- 같은 단지·같은 평형을 다시 보면 중복으로 쌓지 않고 맨 위로 올립니다
- 항목을 누르면 그 조회로 되돌아갑니다. 다른 시군구였다면 상단 필터도 같이 맞춥니다
- 단지를 빠르게 연달아 누르면 요청이 겹치는데, **화면은 마지막 요청만** 반영하고
  (늦게 온 옛 응답이 화면을 되돌리지 못하게) **기록은 완료된 조회를 모두** 남깁니다

응답 태그명은 영문(현행 `1613000` 서비스)과 국문(구 `openapi.molit.go.kr`)을 모두
받아들이도록 별칭 매핑을 두었습니다. `aptSeq`(단지 일련번호)가 없으면
`법정동+단지명+지번` 으로 대체 키를 만들어 단지 묶기가 깨지지 않게 했습니다.

### 전월세 · 전세가율

전세 추정은 매매와 **같은 기계**를 씁니다. 전세 보증금을 매매의 `amount` 자리에 옮겨
`buildRegionIndex` + `estimate` 를 그대로 태웁니다 — 통계적으로 같은 문제이고, 이렇게 하면
지수 환산·이상치 제거·면적/층 가중이 공짜로 따라옵니다.

- **월세 계약은 전세 추정에서 제외**합니다. 전월세전환율로 환산할 수는 있지만 그 비율이
  시기·지역마다 달라 오차를 키웁니다. 월세는 따로 집계만 합니다 (보증금/월세 표기)
- 전세가율 = 같은 평형의 **전세 추정 ÷ 매매 추정** × 100. 두 추정 모두 오차가 있으니
  비율도 그만큼 흔들립니다
- 보증금이 있는 월세(반전세)는 월세로 분류합니다

**전월세는 최근 1년만 담습니다** (매매는 3년). 신고량이 5배라 저장 비용이 커서인데,
막상 줄여 보니 추정이 더 좋아졌습니다 — 은마 84.43㎡ 에서 예측구간이 6.80~9.68억에서
7.03~9.49억으로 좁아지고, 모델을 거치지 않은 신규 계약 중위값과의 차이도 0.9% → 0.1%
로 줄었습니다. 오래된 계약이 노이즈였던 셈입니다. 응답도 4.7초 → 1.8초.

전월세 API 에는 **`aptSeq` 가 없어서** 단지를 (법정동 + 단지명 + 지번) 으로 맞춥니다.
지번 표기가 어긋나면 (법정동 + 단지명) 으로 한 번 더 시도하고, 공백 표기 차이는 무시합니다.
화면에서는 매매와 **병렬로** 호출해서(`/api/rent`) 매매 결과가 먼저 뜨고 전월세가 나중에
채워집니다 — 한 응답에 합치면 단지 조회가 통째로 느려집니다.

### 반영되지 않는 것

동/향/층별 조망, 리모델링·인테리어, 급매 여부, 호가, 학군 변화, 재건축 진행 단계,
전세가율, 대출 규제 변화. **참고용 추정치입니다. 투자 판단의 근거로는 부족합니다.**

## 7. 자주 나는 문제

**`공공데이터포털 오류 30`** — 해당 API 활용신청이 안 되어 있거나 키가 틀렸습니다.
[15126468](https://www.data.go.kr/data/15126468/openapi.do) 에서 활용신청 상태를 확인하세요.
승인 직후 몇 분간은 반영이 늦을 수 있습니다.

**`공공데이터포털 오류 22`** — 일일 트래픽(개발계정 10,000건) 초과입니다. 다음 날
초기화되며, 운영계정을 신청하면 늘릴 수 있습니다. Supabase를 붙이면 호출량이 크게 줍니다.

**특정 시군구에서 거래 0건** — 코드가 낡았을 수 있습니다. 시 코드로 부르면 **오류가 아니라
0건**이 돌아와서 조용히 빈 지역이 되니 주의하세요. 실제로 일괄 적재 중 부천(41190)과
화성(41590)이 이렇게 걸렸습니다 — 둘 다 일반구가 설치돼서 시 코드가 무효였습니다.

```bash
npm run probe -- 지역명      # 코드가 데이터를 주는지 확인
npm run probe -- --raw 11680 # 원본 응답 태그 확인
```

일반구가 있는 시(수원·성남·고양·용인·부천·화성·창원·청주·천안 등)는 **구 단위 코드**를
써야 합니다. 강원 42→51, 전북 45→52 처럼 개편된 코드는 자동 폴백이 들어 있습니다.

**용량이 한계에 가까울 때** — 무료 티어 92%를 넘으면 **새 지역** 수집을 거절합니다
(`src/lib/capacity.ts`). 이미 담아둔 지역의 조회와 갱신은 그대로 동작합니다. DB 가 꽉 차서
쓰기가 전부 막히면 기존 지역까지 갱신이 멈추기 때문에, 그 전에 선을 그어 둡니다.

**"누락된 달"이 갑자기 많이 보일 때** — PostgREST 는 요청당 기본 1,000행에서 조용히
잘립니다. 전체 조회는 반드시 `fetchAllPaged`(`src/lib/supabase.ts`)를 쓰세요. 이 프로젝트에서
같은 실수를 세 번 했습니다 — 전월세 조회에서 최근 6개월이 사라졌고, `db:check` 커버리지
리포트가 지역이 28곳을 넘자 있는 데이터를 "누락"으로 잘못 보고했습니다.

**단지명이 같은데 따로 나옴** — 국토부 `aptSeq`(단지 일련번호) 기준으로 묶습니다.
같은 이름의 다른 단지는 실제로 별개이며, 재건축 등으로 일련번호가 바뀌면 갈라집니다.
